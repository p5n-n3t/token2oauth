# Token2OAuth supervisor runtime alignment

This change connects the opt-in Node supervisor runtime to the current Python SQLite assignment registry and operation outbox. Normal gateway startup remains unchanged; only `serve --supervisor-config <private-json>` starts the bridge and provider worker. Node retains OAuth and encrypted account credentials. Python receives account eligibility and session metadata only, never credentials.

The runtime registers `/v1/accounts` using the exact Python DTO: `accountId`, `enabled`, `authorized`, `allowUnknownQuota`, `health`, `quota`, `localCapacity`, and `registeredSessions: [{id, model, workspace}]`. The private config now requires `workspaceId` on each registered session. Unknown quota is accepted only because the strict root config must explicitly set `allowUnknownQuota: true`; known depleted signals and disabled, unauthorized, unsupported, or unhealthy accounts are excluded on every submission and rechecked before each provider mutation. Legacy `generic-bearer-mcp` accounts are eligible only when the configured upstream URL canonically equals LightSprint's documented native MCP endpoint; the same account-pinned `LightSprintJobsAdapter` performs execution.

Each validated DAG task is pinned at submit time to a configured session, walking the eligible registered-session list deterministically in round-robin order. The selected account and session are immutable in Python. Account registration sets `localCapacity: 1`, so SQLite cannot dispatch two active tasks against the same account/session at once; separate accounts may run concurrently up to `maxWorkers`. A bounded text output declares a literal single-line `expectedMarker` (1–256 characters); the same exact string is appended to task instructions and passed unchanged in the Python assignment. Python currently checks literal substring presence rather than enforcing line boundaries. This integration increment rejects fresh launches and non-text outputs because the current Python validator only accepts registered existing sessions with bounded text output.

MCP assignment submission, status, results, and cancellation carry internal `X-Owner-Principal: oauth-client:<clientId>` and `X-Client-Id` headers across the private socket. Status/results/cancel use Python's owner-aware assignment routes; results are projected to bounded camelCase task DTOs. This protects assignments created through MCP. The existing Python compatibility logic treats null owner/client fields on older administrator-created rows as a wildcard, and the documented API does not return ownership metadata; strict exclusion of those legacy rows remains blocked on a Python-side change. MCP cannot invoke global pause/emergency-stop operations, and `job_inbox` returns an explicit unavailable error: the current Python event endpoint has no owner/client/project filter. `job_workers` reports configured sessions and fresh local eligibility signals, with capacity left `unknown`; it does not claim remote slot capacity.

The admin `readAdmin` route now returns the R27 `SupervisorSnapshot` structure. It reads at most 50 assignments for the requested configured project by querying each configured OAuth client's owner-filtered list, then fetches persisted task rows with the same trusted owner/client context. It maps actual provider/account/workspace/session/job/task state and the latest 50 global events that can be matched to that project or its visible assignments. Capacity and account quota fields are omitted because no live denominator or remaining-credit value is available; a 429 remains an unknown quota signal. Admin inbox contents are not supplied because the current Python bridge has no scoped inbox route.

Configured session IDs must be unique across projects. Python account capacity is set to one concurrent operation per account, a conservative lock that also prevents concurrent reuse when multiple registered sessions share an account; two account bindings cannot register the same session ID in one runtime configuration.

The worker starts after successful account registration and stops before bridge shutdown. Its operation receipts and assignments remain in Python SQLite across Node restarts. The Python child inherits umask `0177`, so its Unix socket inode is created as `0600` from the first instant; Node rejects any other mode. Ambiguous provider mutations remain classified as ambiguous; the worker does not replay them. A narrow Node-to-Python receipt compatibility projection converts the current worker's ISO `assistantAt` to epoch seconds and its `assistant_result_ready` status to the Python observer's `idle` state. This can be removed when the separately-owned worker projection matches the Python contract directly.

## Verification and current limits

`npm test` exercises the real Python Unix-socket process with fake account-pinned adapters: two-account dispatch, bounded marker completion, caller isolation, restart persistence, and result reads. No external LightSprint call is made. The Python registry currently leaves the assignment-level state `queued` even after all task rows are `complete`; its `record_result` counts remaining tasks before updating the final task state. The integration test therefore verifies completed task rows and durable result artifacts, not a corrected parent state. The Python job runtime also has no owner-scoped inbox or project-scoped pause endpoint; neither is approximated with the global endpoints.
