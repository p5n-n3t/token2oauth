# Durable job worker implementation

Implemented on `feat/t2o-job-worker-20261010` from `origin/codex/unified-platform-20261010` (`d229bbc`). The new `createJobWorker` has explicit `start`, `stop`, and `tick` controls, no import-time activity, timeout-bounded bridge calls, a validated lease, a configurable concurrency ceiling, duplicate-operation fencing, and polling through the private operation claim/result routes. It accepts an injected account-pinned adapter and a separate current-account eligibility predicate.

`chat_session` validates the pinned session owner, send permission, idle state, and registered `gpt-6-luna` model before issuing exactly one adapter chat call with the durable client message ID. It rechecks account eligibility immediately before sending. The configured adapter timeout is passed to the factory and checked against the claim lease with room for result posting. A thrown or ambiguous chat result is reported ambiguous and never replayed. Lost result acknowledgments retain the identical receipt in memory and retry only result posting. Shutdown clears timers, aborts a pending claim, prevents queued work from starting a provider mutation, and drains already-started work.

`observe_session` fetches status, reads a size-bounded transcript only when idle, and selects the newest assistant entry at or after `input.dispatchAt`. The normalized result contains only bounded assistant text/time and session status/model identifiers, not the provider transcript. `cancel_session` reports cancellation accepted only after `stopSession` succeeds and a follow-up status confirms a stopped/cancelled state. Fresh task creation, patch, packet verification, and launch are disabled by default. Their opt-in paths require complete inputs; patch, verify, and launch require exact instruction readback. Launch additionally requires an adapter method that requests and reports `gpt-6-luna`, which the current stock LightSprint adapter does not expose.

## Dependency and contract notes

- Both requested refs were fetched: `origin/feat/t2o-supervisor-bridge-20261010` (`d20bfe8`) and `origin/feat/t2o-lightsprint-jobs-adapter-20261010` (`a4655b7`). Neither is an ancestor of the selected base. The account-pinned adapter exists in the base; the bridge implementation does not. This worker therefore accepts a bridge with the fetched `SupervisorBridge.request(method, route, body, options)` shape and does not wire or modify unowned runtime modules.
- Inspection of the available durable registry ref `origin/feat/t2o-durable-jobs-20261010` showed its older operation input contains assignment/task/phase only, and its result allowlist excludes `assistantText` and `assistantAt`. The worker follows the assigned R21 envelope/result contract and emits those two bounded fields for fresh observations; integration against that older registry snapshot requires its DTO/schema to be updated first. No registry or bridge source was changed here.
- No provider calls or paid operations were executed. The worker is not enabled by default; a runtime owner must instantiate it with the current account predicate and explicitly call `start()`.
