# Additional agent and workspace integrations

**Verified:** 2026-10-10. **Scope:** official vendor documentation only; repository context was Token2OAuth 0.2.0, an OAuth facade and encrypted credential pool for bearer-token MCP servers. Eight primary reference pages were opened alongside targeted official-site searches. No integration APIs were executed; no accounts, sandboxes, projects, API keys, or paid operations were created. “Documented,” “experimental,” “unsupported,” and “unknown” describe evidence status, not observed live behavior.

## Recommendation

For Snooze’s repository coding workflow, prototype a small **GitHub Copilot cloud-agent task provider in Snooze**: submit a task, poll its task status, and return the resulting branch or pull request for review. Keep GitHub authorization direct and repository-scoped. Do not turn Token2OAuth into a general agent/compute orchestrator: Copilot’s task API is REST, not an upstream MCP server, and Token2OAuth’s current proxy cannot consume it directly. This is the clearest documented managed-agent lifecycle and yields Git-native review artifacts. The REST API is in public preview, however; cancellation, webhook delivery, and exact entitlement pricing were not confirmed in the reviewed task reference. Treat those as launch gates, not implementation details to guess.

Smallest useful adapter: `start(prompt, repo, base_ref)`, `get(task_id)`, and a bounded polling loop with backoff. Persist only the GitHub task ID, repository, state, and returned branch/PR URL. Add cancellation only after GitHub documents a supported cancel operation; do not equate a `cancelled` state with a callable cancel endpoint. Use existing GitHub app/user authorization with the documented permissions, avoid copying user tokens into the Token2OAuth credential pool, and require a human review of branch/PR output. Add webhook handling only if GitHub documents a supported task event; polling is the confirmed MVP.

## Fit and maintenance judgment

GitHub Copilot is the recommended first adapter when Snooze’s unit of work is a repository task and a branch/PR is the desired artifact. It delivers agent execution rather than just GPU or VM time and has a narrowly scoped repository permission. Its public-preview status, unverified cancellation contract, and unverified billing allowance make a cautious, read-after-start MVP essential. If durable arbitrary code execution is the actual need instead, E2B is the better bounded compute API, but it introduces metered runtime and sandbox cleanup rather than solving model/agent lifecycle. Daytona is a credible alternative where persistent workspace semantics matter. Keep v0, Lovable, and Replit as product-specific app-generation or deployment connectors; none is a generic interchangeable agent runtime. Nebius is best considered a model/GPU provider, not a turnkey managed agent.
